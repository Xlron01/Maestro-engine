# خطة TASK-038 — Compliance Runtime Layer (فوق النواة الحالية، بلا أي إعادة تصميم) — rev.2 (معتمدة مع توضيحين توثيقيين)

## 0) الحدود المقفولة من رسالة المالك
- **Tests-first**: PASS/FAIL criteria والاختبارات تُكتب وتُجمد قبل كود الـresolution. لا Formula للـCompliance ولا weights مخترعة.
- **العقود مقفولة حرفيًا**: Authority (RelevanceControl موجود — لا ChainControl جديد، Membership ≠ Authority) · Influence (structural + informal، contextual query، لا global score) · Legitimacy (4 domains، primitive facts + derived states ملك لغيرها، PARTIAL عند نقص PopularSupport/ConstitutionalValidity) · Capability (feasibility = FEASIBLE|INFEASIBLE|UNKNOWN، status = COMPLETE|PARTIAL، استهلاك World Facts الخام مشروع — قاعدة "Capability تستهلك ولا تملك") · Coercion (future dependency فقط — لا FearSystem) · Compliance (بُعدان مستقلان: compliance_degree 0..1 + resistance_mode NONE|PASSIVE|ACTIVE + resistance_strength، بلا probability).
- **الترتيب المقفول**: Gate 1 = Feasibility (INFEASIBLE+COMPLETE ⇒ short-circuit بلا اختلاق compliance؛ UNKNOWN+PARTIAL لا يوقف) → Stage 2 = contextual assessments فقط ما يحتاجه الـaction، بلا سلسلة dependency قسرية → Stage 3 = deterministic resolution تركيب أدلة (v0 minimum).
- **Dependency availability**: نقص ⇒ `status=PARTIAL + missing_inputs[]` — لا defaults، لا false كاذب، لا بناء النظام الناقص.
- **ممنوعات صريحة**: لا Military/Geography/PublicOpinion/Constitutional/Fear/Punishment systems، لا Scheduler/EventQueue جديد، لا global scores، لا probability، لا per-tick polling، لا NxN matrices، لا duplicated economic dependence.
- **Determinism**: نفس state+inputs = نفس result، صفر stochastic.
- **صفر تعديل** على النواة التسعة وعلى Simulation/EventQueue/Scheduler/dispatch.json/طبقة المحتوى الإنتاجية.

## 0-b) التوضيحان المعتمدان من المراجعة (التزام توثيقي ملزم — لا تغيير تصميم)
1. **social_relations = قاموس واحد متعدد القنوات لكل edge** (`social_relations[target] = {loyalty, trust, kinship, ...}`) — **ليس** قاموسين منفصلين لكل ظاهرة. Influence يقرأ قناته (trust/kinship) وCompliance يقرأ قناته (loyalty) **من نفس الحقل الخام**. يُكتب نصًا صريحًا في: هيدر `compliance_types.gd` + هيدر `influence_query.gd` + هيدر `compliance_query.gd` + قسم العقود في وثيقة 27، بصيغة: "قراءة قنوات مختلفة من نفس الـedge — ليست نسخًا مستقلة من المفهوم لكل نظام".
2. **عقد استخدام control_chains (precondition موثق)**: مسؤولية الـcaller (طبقة المحتوى لاحقًا) هي استدعاء `RelevanceControl.control_chains()` مرة واحدة وتمرير ناتجه في الـcontext قبل أي query من الطبقة. Compliance **لا تحسبها بنفسها ولا تفترض وجودها إلا كمدخل**. يُكتب في: هيدرات الوحدات الخمس + وثيقة 27 (قسم "Usage Contract")، بصيغة precondition صريحة: "المستدعي يجب أن يمرر chains محسوبة مسبقًا؛ غيابها = missing_inputs للـassessments المعنية بPARTIAL — وليس إعادة حساب".

## 1) قرارات تصميم معلنة (مع التبرير)
1. **موقع الطبقة**: ملفات جديدة في `scripts/compliance/` (نمط `economy/` و`relevance_*.gd`) — صفر لمس kernel.
2. **صيغة العالم للعقود**: schema كيانات Model v1 (`authority[{to,degree}]` / `possession` / `stance` / `relations` / `goal_table`) — نفس صيغة بنية Authority الحالية؛ "الربط بدون إعادة كتابة" = استهلاك `RelevanceControl.control_chains()` ناتجًا جاهزًا. تكييف countries-format مؤجل (future work موثق).
3. **ملكية الحساب**: الـcaller يحسب control_chains مرة واحدة ويمرر الناتج (انظر عقد الاستخدام §0-b-2) — لا إعادة حساب لكل query، ولا caching subsystem خاص إلا ببرهان benchmark.
4. **لا ربط بمسار الإنتاج**: Compliance استعلام on-demand؛ لا تسجيل في dispatch.json ولا استدعاء من run_step — التبرير: أي wiring إنتاجي يتطلب قرارات formula خارج النطاق ويخاطر بكسر L. (اختبار K يثبت: صفر تقييمات أثناء التشغيل.)
5. **الـconfig**: `data/rules/compliance_config.json` بعتبات v0 بيانات-مدفوعة، كل قسم موسوم `NON-FINAL`.
6. **العلاقات الاجتماعية sparse**: شكل مستهلَك فقط (لا نظام): قاموس واحد متعدد القنوات لكل زوج (انظر §0-b-1).
